## Where it started

The first audit put mobile performance **in the 40s on the main landing pages, and under 30 on the heaviest dynamic pages**. Most of the cost was code and media the first view didn't need.

## What I changed

- **Lighter media.** Heavy background videos became compressed, cached images.
- **Third-party scripts wait their turn.** A third-party security script moved from loading up front to loading lazily, then to loading only when a visitor first interacts.
- **Heavy UI providers load lazily.** The component library's configuration provider no longer blocks the first render.
- **Idle-time rendering.** Work that isn't needed for the first view is deferred until the browser is idle.
- **Render only what's on screen.** I rebuilt the visibility component on React's external-store hook, so off-screen parts stay unrendered without extra re-renders.
- **Leaner state.** The main store moved from a context provider to a singleton, so updates stop re-rendering whole trees.
- **A lighter component library.** Replaced a heavy component library with a design system of my own, with about half the JavaScript. [Read more](/highlights/design-system)
- **Rendering strategy per page:** server rendering, static generation and incremental regeneration where each fits, plus lazy loading, image optimisation and code splitting.

## How we keep it fast

- **A monthly performance review.** Every month, Lighthouse runs on every key page template, on desktop and mobile. Each month ends with countermeasures, and the next month checks whether they worked.
- **Changes ship in stages.** If a score drops, we know which change caused it, instead of untangling ten at once.

## What I took from it

**The fastest code is the code that doesn't run on first load.** And speed isn't a project you finish — pages drift slower with every feature, so it has to be measured every month.
