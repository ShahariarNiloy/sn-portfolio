## The search box that waits

Picture someone opening a travel site on a phone. They know where they want to go. They have dates in mind. All they need from us is a search box that works.

Between them and that search box sits everything the browser has to download, read and run first. Some of it is the page. A lot of it is the toolbox the page was built with: the buttons, the selects, the date picker, and the machinery that styles them.

On a booking site, **bundle size is conversion**. Every kilobyte delays the one thing the visitor came to do, and they can always go and do it somewhere else.

Our toolbox was a component library, and it was heavy. It carried a styling runtime, which is JavaScript that works out the styles in the browser, and far more code than the platform needed. And a component library is awkward to replace, because screens depend on how it behaves as well as how it looks.

## The rule

A rebuild like this usually fails in one of two ways. Either the new library is so different that every screen has to be rewritten, and the migration never ends. Or it's a thin wrapper around the old one, and nothing gets lighter.

So I worked from one rule: **keep everything the team relies on, and drop everything else.**

Keep the props. Keep the hover and focus states, the keyboard behaviour, and the density of the layout. Drop the styling runtime, and the code the platform didn't need.

Keeping the API meant that moving a screen over was mostly **an import swap**. Change where the component comes from, and leave the rest of the screen alone. The names here are made up, but the shape is the point:

```tsx
// Before
import { Select } from 'previous-library';

// After: same props, same behaviour
import { Select } from '@/design-system';
```

An engineer who knew the old library already knew the new one.

That rule has a cost. When you promise the same API, you inherit someone else's decisions, including the ones you'd have made differently. I think that's a fair price. A cleaner API that asks every screen to change has to be paid for by everyone. A familiar one is paid for once, by whoever builds it.

## Building it from the inside out

The components are React and TypeScript, styled with Tailwind CSS. They lean on a few small helpers, and almost nothing else. Styles live in a stylesheet, so there's no runtime working them out while someone waits.

The simple pieces are easy to picture. A button is a button. The harder ones are the widgets a travel site depends on: the date picker, the time picker, the select, the data table. Each has a lot to remember: what is open, what is highlighted, what the arrow keys do, where focus goes when it closes.

Those are built **headless first**. The logic lives in hooks, and the styles are layered on top. The hook knows how a select behaves; it doesn't know what one looks like. A simplified sketch:

```tsx
function Select({ options, value, onChange }) {
	// Behaviour: open state, highlight, keyboard, focus.
	const select = useSelect({ options, value, onChange });

	// Appearance: markup and token-based styles.
	return <SelectView {...select} />;
}
```

That makes a widget easier to test, because its behaviour can be checked without its appearance. It also means it can be reskinned without being forked.

Underneath, nothing uses a raw value. Every colour, space, shadow and motion value comes from **tokens**, with paired light and dark modes. A token is only a name for a decision, but it means the decision is made once. Change it there, and every component agrees.

The last structural choice was about loading. Everything is tree-shakeable, so a screen that imports a button gets a button. The heavy parts load only when they're needed, and all of it is safe to render on the server.

## The parts you can't see

Size was the reason to start. It wasn't allowed to be the only thing that mattered, because it's easy to make a component smaller by leaving out the parts most people don't notice.

Accessibility is the first thing that gets left out that way. Here it was part of the definition of finished: WCAG AA as the baseline, standard ARIA patterns, full keyboard support and managed focus. **If it isn't accessible, it isn't done.** Putting that in the component means nobody has to remember it on every screen.

Travel brings its own demands. The platform runs in 26 languages, so right-to-left text and long translations can't be edge cases. A label that fits neatly in English may need a lot more room somewhere else. Booking screens are also dense, with prices, dates and rooms all competing for space. The components handle these from the start.

Motion got the same treatment. The language is calm: purposeful, brief, never bouncy. Every component transition is **300 ms or less**, and exits are faster than entrances, because someone closing a menu has already moved on. Reduced motion is respected everywhere. Movement becomes a fade, and autoplay and shimmer stop.

## Was it lighter?

"It feels faster" isn't a result, so each component was measured against the one it replaced. Both were bundled on their own, then minified, tree-shaken and compressed, in the same way. Framework code was left out, since the app ships it either way.

### Reading the numbers

The data table came down by 91%. Even the button, about as simple as a component gets, came down by 75%.

Two things are worth saying about those numbers. The first is that "about half" and "around six times smaller" are both true, because they answer different questions. One is the whole library; the other is a typical component on its own.

The second is that the comparison has a tilt. Styles in a shared stylesheet aren't counted in a per-component bundle, while a library that styles with JavaScript carries its runtime in the total. The runtime is a real cost, so it belongs there. But the stylesheet is a cost too, and anyone reading the chart should know it isn't in it.

## Becoming the default

A design system isn't finished when its components are. It's finished when people stop choosing whether to use it.

It's now **the standard for all new UI** on the platform, and [one part of a wider performance effort](/highlights/performance). It sits beside lighter media, third-party scripts that wait their turn, and a monthly review that catches pages when they drift. I wouldn't credit it with those results on its own. What it does is lower the starting point: a new screen begins lighter, before anyone has optimised anything.

That's the part I like most. Most performance work has to be remembered. Someone has to notice a slow page, find the cause and fix it, and then do it again when the next feature lands. This is different. The light version is simply the one you get when you import a button.

## What I took from it

**Compatibility is a feature.** The smallest component library in the world helps nobody if moving to it means rewriting the product.

**Make the right thing the easy thing.** Accessibility, right-to-left text and reduced motion last longer inside a component than on a checklist.

**Measure in a way you'd be happy to explain.** Include the parts that don't flatter you. The numbers were good enough to be honest about.

And the person on the phone never sees any of it. They see a search box, a little sooner.
