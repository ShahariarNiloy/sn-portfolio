## The problem

Interactive components need their text **on the very first render** — on the server and again while React hydrates — or visitors see raw keys or a flash of English. The simplest way to guarantee that was to embed the whole dictionary in every page.

It worked, but it put about 60 KB of compressed text (nearly 200 KB raw) into every page before it could render. No page needed most of it: even the busiest pages use only a few hundred of the thousands of keys.

Over a five-page visit (home, hotels, a listing, a hotel, flights), that's about **5 × 60 = 300 KB before**, against about **31 + 61 = 92 KB after** on the first visit (about 70% less), including the full dictionary, and about **31 KB** on later visits (about 90% less). In Japanese, where characters take more bytes, each page saves even more.

## Between pages

Moving to another page doesn't wait for the full dictionary. The next page brings its own words inside the page data Next.js fetches, and prefetched links already include them, so the text is right from the first frame. Only keys built at runtime show the English fallback until the full dictionary arrives. Changing language is always a full page load.

## The mistake that taught me the most

My first version **preloaded** the full dictionary at low priority. On a throttled phone it still competed with the page's largest image and pushed the home page's Largest Contentful Paint back by **1.7 s**. Moving it to after load, at the next idle moment, removed the cost completely.

## Guardrails

- **The build fails** if a page or layout isn't wired up to receive its words, so nothing ships half-translated.
- **An escape hatch for keys built from data**, like a status code or a country name, so they can still travel with the page.
- **Every string has an English fallback**, so a missing translation shows readable text, never a raw key.

The rest of the locale system (language in the URL, right-to-left layouts, local dates and prices) is part of the wider [adventure.inc platform](/work/adventure-inc).

## What I took from it

**Measure what's inside the HTML, not just the JavaScript bundle.** The bytes that arrive before the page can render matter most — and they're the easiest to forget.
